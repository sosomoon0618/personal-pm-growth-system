## A. 项目目标与成功标准

### 目标

建立一套让岗位准备、真实面试、复盘、能力训练、日常产品工作和知识资产更新形成闭环的个人成长系统。

### 成功标准

1. 每个重点项目均有可追溯的事实证据，项目讲稿和口头答案均能回链到事实。
2. 每次真实面试均保留原始问题与原始回答，并能形成有验证标准的改进任务。
3. 能区分并关联母题、真实问题、答案、SOP、项目证据和训练任务，而不重复维护正文。
4. 复盘能推动实际工作方法、SOP、模板或项目事实的改进；任务完成不自动等同于能力改善。
5. AI 自动化只读取所需上下文，所有重要更新都有来源、版本、状态和可检验结果。
6. 维护成本可控：核心结构稳定，非重点历史项目只保留框架和最低必要事实。

## D. 目标文档结构及职责

新知识库建议建立“个人产品能力与面试成长系统”入口页，并采用以下结构（实施前须经阶段门禁确认）：

1. **个人上下文与职业目标**：当前背景、求职方向、边界条件、目标优先级和更新依据。
2. **项目经历资产**：按项目组织的完整叙事、事实说明、讲稿、相关 PRD 链接及材料入口；不作为事实的唯一存储位置。
3. **面试准备与岗位研究**：岗位分析、准备包、母题索引、使用说明。
4. **面试复盘与能力改进**：复盘原则、评分口径、训练机制与复盘入口。
5. **产品方法论、SOP 与模板**：需求全生命周期总入口，以及需求分析、优先级、数据和上线复盘、AI Evaluation、AI Bad Case 等的实际归属。
6. **Skills 运行手册与维护规范**：Skill 职责、输入输出、数据写入边界、验证用例与变更记录。
7. **架构决策与变更记录**：核心架构变更及其证据、影响、回滚方式。

### 归属规则

- 完整阅读、推理和执行所需的正文写入文档。
- 表格字段口径、视图导航、使用教程可写入主 Base 内说明页；完整方法论仍保留在知识库文档。
- “需求全生命周期模板”是 SOP 体系的一部分，不与工作知识体系并列。
- 未经证据审计前，不决定细分资料是独立 SOP、子章节还是配套模板。

## E. Base 边界方案、数据表与关联关系

### 先确定对象边界，再决定一个或多个 Base

知识库是整个系统。Base 是其中为高频结构化协作、关联、筛选和状态流转而设置的工作单元；一个 Base 可以包含多个数据表和配套说明文档。P0 审计后，应在下列两种方案中基于实际证据做选择：

| 候选方案 | 适用条件 | 预期内容 |
|---|---|---|
| **方案 A：成长运营 Base** | 对象总量可控，岗位准备、面试、训练、能力和知识资产变更高频互联。 | 岗位、母题与答案、面试复盘任务、能力短板、SOP 资产和变更记录。项目事实仅保留索引与关键证据链接。 |
| **方案 B：项目证据 Base + 成长运营 Base** | 项目和需求事实数量大、PRD／生命周期追踪复杂，或项目资产需要独立维护节奏。 | 项目证据 Base：项目、PRD、需求、关键事实、需求复盘。成长运营 Base：岗位、母题与答案、面试、能力、训练、SOP。两个 Base 用稳定链接或少量关键关联连接。 |

**定稿判断标准：** 项目和需求条目规模、关联复杂度、查询视图、维护频率、权限边界、飞书 Base 的实际跨表／跨 Base 能力以及用户日常使用习惯。未经审计不选择方案 A 或 B，也不创建空表。

### Base 内文档的职责

Base 内说明文档可承载字段词典、状态定义、视图导航、录入示例、数据质量规则和本 Base 的局部工作流。完整项目复盘、完整 SOP、长篇岗位分析和逐字讲稿仍应维护于知识库文档，并在 Base 内建立链接与版本关联。

### 不应放入 Base 正文的内容

- 完整项目复盘、复杂 SOP、长篇岗位分析、逐字讲稿、知识文章、深度推理和大量附件说明。
- 这些内容应在知识库文档中维护，并由 Base 记录链接、版本、适用范围和状态。

### 表格清单

| 表名 | 职责 | 最小关键字段 | 主要关联 |
|---|---|---|---|
| 个人目标与上下文 | 管理职业方向及约束 | 目标、优先级、证据链接、更新时间、状态 | 岗位、能力 |
| 岗位与公司 | 管理目标公司、JD 与匹配 | 公司、岗位、JD 来源、要求、匹配度、状态 | 准备包、母题、场次 |
| 项目档案 | 覆盖全部项目的元数据、优先级与材料入口 | 项目、重要度、阶段、叙事链接、PRD 链接、状态 | 项目事实、经历资产、需求 |
| 项目事实库 | 唯一事实源 | 事实 ID、项目、阶段、事实、数据、来源、时间、确认状态 | 经历、答案、SOP、复盘、需求 |
| 需求与价值复盘 | 为高价值需求建立从 PRD 到上线验证的可回溯复盘，而非复制全部需求单 | 需求、所属项目、PRD 链接、价值判断、关键决策、生命周期状态、复盘链接、沉淀状态 | 项目、事实、SOP、训练 |
| 项目经历资产 | 管理可讲述的项目版本 | 经历 ID、项目、用途、版本、核心证据、缺口、状态 | 项目事实、答案、岗位 |
| 面试母题库 | 稳定问题主题 | 母题、能力标签、评分标准、追问、适用范围 | 答案、真实问题、SOP |
| 母题与答案资产 | 在同一表中管理母题和其答案版本，通过视图区分主题管理、答案迭代与练习状态 | 记录类型、母题、回答版本、讲稿、证据、练习状态、适用岗位、状态 | 岗位、事实、真实问题、训练、SOP |
| 面试场次 | 管理真实面试事件 | 公司、岗位、日期、轮次、结果、复盘状态 | 真实问题、岗位 |
| 真实问题与复盘 | 仅管理需要诊断、沉淀或推进改进的真实问题；保留对完整原始面试记录的链接 | 原始问法、原始回答摘要、原始记录链接、参考母题、评分、根因、优先级、状态 | 场次、母题与答案、训练、事实 |
| 能力与短板 | 汇总能力现状、证据、改进建议与验证结果 | 能力、定义、当前等级、证据、短板、建议方案、验证标准、验证状态 | 母题与答案、训练、SOP |
| 训练与工作改进任务 | 推进有验证的行动 | 任务 ID、任务类型、根因、行动、验证标准、截止日、状态 | 复盘、能力、事实、SOP |
| SOP／方法论资产 | 管理可执行方法和模板 | 主题、类型、版本、适用范围、来源、验证状态 | 母题、任务、事实 |
| 知识资产变更记录 | 记录重要更新与回滚 | 资产、变更、原因、证据、批准、回滚位置 | 全部核心表 |

### 关系规则

1. 母题是主题；真实问题必须保存原始问法、出现的面试场次和当时回答。
2. 母题和面试答案在同一表内，以“记录类型／关联母题／版本／视图”区分；答案服务于面试表达，SOP 服务于真实工作，两者可关联但不能互相替代。
3. 项目经历是叙事资产；项目事实库是证据来源。事实被更正时应保留变更记录。
4. 每场面试的完整原始记录默认保留在专门的面试记录文档中；表格只录入值得复盘、需训练、可沉淀或需跟踪的问题，并链接回原文。通过视图区分“全部原始面试记录索引”“待复盘”“可沉淀”“仅留档”。
5. 能力短板必须至少包含一个改进建议、可执行任务或明确标注“待诊断”；训练任务必须有验证标准，任务完成不等于能力改善。
6. 未确认事实、AI 推测和待验证假设必须以独立状态记录，禁止混入确认事实。

## F. 端到端流程

1. 录入或更新个人目标、目标岗位与 JD 来源。
2. 识别岗位要求、可用项目证据与能力缺口，形成岗位准备包。
3. 从项目事实、母题与答案资产和 SOP 生成或更新讲稿、答案与追问准备。
4. 为每场真实面试建立完整原始记录文档，并在场次索引中关联该文档。
5. 只将值得诊断、沉淀、训练或跟踪的问题录入复盘表，并关联可参考母题或标记“暂无母题”。
6. 对复盘问题进行评分和根因诊断，判断应改进表达、补事实、改工作方法、补 SOP 或训练追问。
7. 在能力短板中记录改进方案建议，建立训练或工作改进任务，并设置可观察的验证标准。
8. 根据验证结果更新相应资产：项目事实、PRD／需求复盘、讲稿、答案、SOP、模板、母题或 Skill。
9. 运行一致性检查；对可能改变多个模块的结论发起架构变更提案。

## G. Skills 审计、改造与调用方案

### 待审计维度

对每项现有 Skill 读取其实际说明、依赖、输入输出、写入权限、示例和重复关系，再作保留／改造／合并／弃用／重写判断。

### 目标 Skill 分层

| 类别 | 目标行为 | 禁止行为 |
|---|---|---|
| 上下文装配 | 按任务最小化读取个人目标、岗位、证据和 SOP | 将未确认信息当作事实 |
| 岗位定制准备 | 将 JD 映射为能力、证据缺口、母题与准备任务 | 泛化套用旧岗位结论 |
| 项目经历与回答 | 基于确认事实生成不同长度表达 | 编造项目数据或结果 |
| 面试复盘诊断 | 保留原始问答，识别表达、判断、证据和方法根因 | 覆盖原始回答 |
| 训练与工作改进 | 将根因映射到训练、事实补充、工作实验或 SOP 更新 | 将所有问题变成背诵任务 |
| 资产更新建议 | 指明应更新哪个资产及其证据 | 未确认即修改核心资产 |
| 一致性检查 | 检查来源、版本、失效引用、证据冲突和闭环 | 将检查推断写回事实库 |

## I. 阶段门禁

每个阶段开始前，必须：

1. 阅读本控制文档的最新状态、前置条件、风险和未解决问题。
2. 展示本阶段的文件、表格、Skills、预期变更与风险。
3. 获得用户对该阶段范围的明确确认。

每个阶段结束后，必须：

1. 对照验收标准检查实际结果。
2. 更新任务状态、决策记录、问题和验证结果。
3. 展示完成项、未完成项和实际变更。
4. 停止，等待下一阶段确认。
